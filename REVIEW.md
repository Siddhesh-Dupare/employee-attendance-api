# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | punch_in() | When the supplied emp_code that does not exists, the database returns None. The function attemps to access emp["shift_start"], causing a TypeError and a server error instead of the required 404 response. | A test that calls POST /attendance/punch-in with an unknown employee code. Before the fix, the request caused a TypeError, after the fix the test passed with HTTP 404. | Added an employee existence check immediately after the databse lookup. If the employee is missing, the endpoint raises an HTTPException with status code 404. |
| 2 | health() | The health endpoint always returned 200 OK without checking whether MongoDB was available. | If MongoDB was unavailable, GET /health would still return 200 OK, incorrectly indicating that the application was ready. | Added a MongoDB ping using client.admin.command("ping"). The endpoint returns 200 OK when the ping succeeds and raises an HTTP exception with status code 503 service unavailable when a PyMongoError occurs. |
| 3 | EmployeeIn.validate_shift_time_format | Shift times were not explicitly validated against the required HH:MM 24 hour format. | Send an invalid shift time format such as "25:00" to POST /employees the request should return 422. | Added a Pydantic validator for shift_start and shift_end to validate the tiem format. Added a test for invalid shift times. |
| 4 | EmployeeIn.validate_shift_times | The employee creation request did not reject identical shift_start and shift_end times. | Send POST /employees with identical shift_start and shift_end times, the request should return 422. | Added a Pydantic validator using mode="after" to compare both the fields also added a test verifying the 422 response and that no employee is inserted. |
| 5 | create_employee() | The employees collection did not have a database-level unique index on emp_code, allowing concurrent requests to create duplicate employee records. | The concurrency test initially returned multiple 201 responses for simultaneous requests using the same emp_code. | Added db.employees.create_index("emp_code", unique=True) during initialization and handled DuplicateKeyError in create_employee() by returning HTTP 409. The concurrency test now verifies exactly one 201, nine 409 responses, and one stored employee document.

Also note anything you looked at and decided was **not** a defect, and why.
